# Campaign Engine — «Яр воин»

Рабочая кампания: `reider789/havengard-campaign-engine`, ветка `main`, campaign_id `yar-warrior`.
Партия: Яр, Дафна, Лютобор, Рада. Канон меняется вследствие сыгранных событий,
явных исправлений и принятых решений игрока.

## Продолжение игры

1. Получить свежий head `main`. Читать `views/scene-context.md` из этого head.
2. Использовать указанную `state_revision`. Подгружать нужные поля state, карточки,
   правила и источники по ситуации. Не читать весь архив и полный GM-отчёт каждый ход.
3. При возобновлении проверить неприменённые `transactions/live/*.json`.
   Наличие файла в live ещё не означает успешного сохранения.
4. Продолжить с точной реплики/фрагмента в `scene_context.handoff`. Если исходного
   ввода нет, не сочинять его; сверить источник, когда пропуск влияет на выбор.
5. Если head и сцена не изменились, использовать уже прочитанное. Перед записью
   проверить ревизию. При смене режима получить `context --mode combat` и т. п.

Навык `heivengard-gm` задаёт порядок работы; постоянные правила находятся в
`rules/_campaign-rules.json`. Полные источники перечислены в `source_registry`.
В бою игрок управляет всей четвёркой; спутники самостоятельны вне выбора боевых действий.

## Сверка города Г1М8

Единственное оперативное сохранение — `state/_campaign-state.json`.
Город: `world.city`; казна: `world.city_treasury_cp`.
Полные правила экономики: `rules/economy-full-g1m8.txt`.
Исторические снимки двадцати вкладок книги сохранены в `migrations/`,
а не используются как второй оперативный реестр.

Сверка по летописи 017 завершена: **221 действующий житель** (222 записи,
включая погибшего Жителя 12), из них **200 назначены**, двое взрослых
Мелания и Теодор Рейн пока не работают. Рейны живут в усадьбе Яра.
В типовых домах **205/240 комфортных мест**, свободно **35/95**.
Подтверждены 38 рабочих точек, 12 драков, 28 городских лошадей.
Четыре частные вельмарские лошади к городскому стаду не прибавляются.

Карточки всех четырёх героев и известное имущество перенесены в
`characters.*.character_sheet` и `inventory_catalog`.
На момент переноса были подтверждены метатель Яра 20/28 и
стрелы Рады 57/60; **это исторические значения, не постоянные лимиты**.
Текущие боеприпасы всегда брать из `characters.*.resources`,
а не из архивных карточек или описаний предметов.

Проверки и адресные операции см. `docs/city-migration-g1m8.md`.
Г1М8 **уже открыт и начальные показатели рассчитаны**: в основном
состоянии казна 13 126,33 зм и резерв 426,43 ПЕ при цели 442 ПЕ.
Число 219 в исторических нормах — население до приезда Рейнов;
текущее 221 включает двух взрослых без назначения. Это не ошибка нормы.
**Г1М8 не закрыт:** закрытие Г1М8→Г1М9 проводить только по игровому
событию в конце месяца; прежние расходы и доходы повторно не начислять.

Городские текстовые сводки сверены после переезда Рейнов. Уточнения
сохранять в городском реестре вместе с исходным числом, не
подменяя текущий остаток историческим.

Для расходников доступна транзакция `adjust_item_quantity` (`id`,
`item`, `delta`): она меняет количество у конкретного персонажа
и удаляет пустую запись при расходовании последнего предмета.
Операция `adjust_resource` для стрел синхронизирует карточку боезапаса.
Проверки не привязаны к неизменности значений из Г1М8.

Новых уровней жилья, правил ресурсов и войск пока не принимали.
Карту v3 ещё нужно подключить к интерфейсу сохранения в GitHub.

## Источники истины и производные файлы

| Файл | Назначение |
| --- | --- |
| `state/_campaign-state.json` | Единственное текущее состояние, включая граф знаний и квитанции событий |
| `rules/_campaign-rules.json` | Правила, характеры, режимы контекста и реестр источников |
| `transactions/applied/*.json` | Неизменяемые payload применённых транзакций |
| `migrations/*.json` | Записи технического переноса формата |
| `views/scene-context.md` | Основной компактный ввод ведущему |
| `views/gm-context.md` | Полный отчёт для аудита; не обязательный ввод каждой сцены |
| `views/player-context.md` | Сводка раскрытых событий/линий и отношений |
| `views/scene-knowledge.md` | Факты выбранных веток и источники знаний участников |
| `state/_knowledge-graph.json` | Производный экспорт графа; вручную не менять |

Не создавать параллельное оперативное сохранение. Excel и сайт не обновляются
от записи в этот репозиторий автоматически. Позднее сыгранное событие из прочитанной
летописи переносить reconciliation-транзакцией с источником.

## Ресурсы, время и неполный импорт

Schema v2 хранит счётчики как `{"current": 20, "max": 28}`; ячейки — по кругам:
`{"1": {"current": 4, "max": 4}, "5": {"current": 2, "max": 2}}`.
Деньги — целые медные монеты (`personal_money_cp`). Ресурсная операция понимает
старую строку `20/28` и переводит её в числовую структуру. Неверные пределы
отвергаются до записи; неизвестное значение не превращается в ноль.

Основной счётчик времени — `world.timekeeping.elapsed_seconds_from_anchor`.
Полные часы и дни вычисляются из него. `advance_time` принимает seconds, minutes или hours; связанные поля
обновляются в том же `build_result`, поэтому preview включает их заранее.
`time_label` описывает сцену и не заменяет часы. Неподтверждённую длительность
не придумывать; приблизительная дата не становится точной из-за миграции.

Пересчёт времени меняет только свои производные поля и `time_summary`.
Ранения, симптомы, решения, исходы и роды не возникают от автоматического пересчёта.
Отдельный `sync_time_dependent_state.py` теперь только проверяет согласованность.

`characters.*.source_coverage` различает complete / partial / not_imported для
инвентаря и карточки. `inventory: []` при неполном импорте не означает отсутствие
вещей. Источник и неизвестная версия отмечены явно. Переносить данные по прочитанному
источнику, не заменяя поздние engine-изменения старыми числами.

## Факты, знания и история

- `status`: canonical / candidate / disproven — отношение записи к истине.
- `temporal_status`: current / historical — применимость к текущему состоянию.
- `superseded_by`, `valid_to_event` — причинный переход к новой записи.
- `known_by` — подтверждённые знания персонажей; явные записи графа awareness
  уточняют knows / heard_of / suspects / believes / misinformed / unknown и требуют источника.
- `characters.*.knowledge` удалён как расходящийся ручной дубль.

Candidate не может становиться знанием. Опровергнутый факт не выводится как истинное
знание; явное заблуждение сопровождается версией персонажа и пометкой об опровержении.
Пустой `scene_knowledge_branches: []` означает отсутствие выбранных веток, а не
автоматическую загрузку всего, где упомянута партия.

Не переписывать текст канонического факта. Добавить новую запись и применить
`supersede_knowledge` для естественного изменения или `correct_knowledge` для ошибки;
указать замену и причину. Историческая запись сохраняется дословно.

События v2 требуют `visibility: party/public/gm`. Ветки без явной видимости скрыты
из player context. GM-инструкции и подготовка не являются публичным каноном.

## Проведение хода

```bash
python tools/campaignctl.py --project . check
python tools/campaignctl.py --project . context --mode combat
python tools/campaignctl.py --project . preview --transaction /path/turn.json
python tools/campaignctl.py --project . commit --transaction /path/turn.json
python tools/campaignctl.py --project . check-views
```

Пример транзакции (123 заменить на текущую ревизию):

```json
{
  "expected_state_revision": 123,
  "event": {"id": "UNIQUE-PLAYED-EVENT", "summary": "Причина изменения.", "visibility": "party"},
  "operations": [
    {"type": "adjust_resource", "id": "yar", "resource": "storm_thrower_ammo", "delta": -1}
  ]
}
```

| Операция | Поля |
| --- | --- |
| `advance_time` | ровно одно из `seconds`, `minutes`, `hours`: целое значение ≥ 0 |
| `adjust_resource` | `id`, `resource`, `delta`; для ячеек ещё `level` |
| `set_character_resource` | `id`, `resource`, `value`: определённый остаток/лимит; изменение максимума требует `capacity_reason` |
| `transfer_money` | `from`, `to`, `amount_cp`; оба баланса должны быть известны |
| `transfer_item` | `from`, `to`, `item`: уже известный конкретный ID |
| `add_knowledge` | `id`, `fact`, `known_by`, опционально `status`, `temporal_status` |
| `supersede_knowledge` / `correct_knowledge` | `id`, `replacement_ids`, `reason`; новую запись добавить той же транзакцией |
| `register_principal` | `id`, `value: {name, kind}` для NPC/группы |
| `set_awareness` | `fact_id`, `principal_id`, `value: {state, source, ...}` |
| `upsert_knowledge_branch` | `id`, `value` со status, knowledge_ids, key_principals |
| `set_scene_context` | `value`: mode, thread_ids, fact_ids, handoff и нужные resource_keys |

При смене `world.current_scene` в той же транзакции явно задать
`set_scene_participants`, `set_scene_context` и `world.scene_knowledge_branches`.
Handoff хранит намерение, нерешённый выбор, точный последний ввод и короткий фрагмент
прозы с источником. Не заполнять пропуски выдуманными цитатами.

`applied_events` не обрезается вместе с последними событиями. Повтор одинакового
ID/payload — no-op даже после смены ожидаемой ревизии; другое содержание с тем же ID —
ошибка. Старый ID без полного payload нельзя проводить повторно. Для закрытия месяца
обязателен верхнеуровневый `unique_key: "month:ГnМm"`. Пересмотр — отдельная поправка.

Локальный commit держит блокировку и атомарно меняет authoritative JSON. Граф,
квитанция и ресурсы входят в эту запись. Сводки производны: после сбоя их можно
перестроить повтором того же события без повторного расхода.

## Работа через GitHub

Есть два маршрута; не смешивать их для одного события:

1. **Коннектор без git-доступа:** загрузить транзакцию в `transactions/live/`, дождаться
   успешного `Apply Live Campaign Transaction`, перечитать квитанцию event_id и ревизию
   из нового head. Только после этого ход сохранён.
2. **Локальная копия:** preview → commit → проверки → один Git-коммит state, views и
   архива → push с проверкой исходного head. Уже применённое событие не класть в live.

Workflow имеет одну очередь записи, начинает с актуального main и публикует файлы
одним Git-коммитом. При изменении main пересчитывает от нового head; устаревшие
предпосылки отвергаются. Не применять force-push или слепой rebase исходов игры.
При сбое сохранить тот же event_id; не отыгрывать событие заново и не обходить отказ
новым ID. Сообщить о сбое и сохранить переносимую транзакцию в чате.

## Проверки и границы автоматизации

```bash
python tools/run_tests.py
```

Проверяются прежние игровые сценарии, числовые пределы, долгий повтор событий,
передача денег, уникальность месяца, часы/дни, сохранение ранений, актуальность фактов,
видимость, смена сцены, одновременные писатели и восстановление сводок.
Fixture-сценарии используют замороженную исходную точку.

Движок не доказывает художественную правду и не заменяет механику D&D. Законность
отдыха, причины доверия NPC и восстановление конкретной способности проверяются
по правилам и источникам до записи. Экономика, сложный количественный инвентарь
и строительство пока рассчитываются по профильным источникам. Новые подсистемы
добавляются по реальной потребности.

Миграция v1→v2: `python tools/migrate_v2.py --expected-revision N` проверяет перенос;
`--apply` выполняет его на изолированной рабочей копии. В живой кампании миграция уже
проведена; повтор возвращает `already_migrated`. Исходный снимок остаётся в Git-истории.

В бою фиксировать порядок инициативы, текущий раунд/ход, позиции и реакции в
`world.combat` через set_world_field; эффекты с точным сроком — у персонажа.
Это явный журнал боевой сцены, не автоматический симулятор действий.
За шестисекундный раунд продвигать `advance_time: seconds=6` один раз в конце
полного раунда, а не после каждого участника. Минуты и секунды не округлять до часов.
