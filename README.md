# Campaign Engine — «Яр воин»

Campaign Engine хранит кампанию в двух независимых слоях:

1. `state/_campaign-state.json` — **что происходит сейчас**: сцена, персонажи, ресурсы, знания, убеждения, сюжетные линии, давления мира, история подтверждённых изменений.
2. `rules/_campaign-rules.json` — **как вести кампанию**: приоритеты канона, стиль повествования, характерные якоря героев, правила боя/ресурсов/путешествий, базовые экономические принципы и реестр полных мастерских источников.

Это разделение принципиально: правила ведения не являются фактами мира и не должны попадать в знания персонажей.

## Источник текущего состояния

`state/_campaign-state.json` — authoritative state.

Во время игрового хода модель/ведущий не редактирует его вручную. Изменение оформляется транзакцией с `expected_state_revision`, проверяется на копии, затем коммитится атомарно. При успешном commit повышается `state_revision` и заново строятся производные контексты.

Команды:

```bash
python tools/campaignctl.py --project . check
python tools/campaignctl.py --project . render
python tools/campaignctl.py --project . preview --transaction transactions/example_update.json
python tools/campaignctl.py --project . commit --transaction transactions/example_update.json
```

## Постоянные правила и большие промты

`rules/_campaign-rules.json` содержит компактные правила, которые нужны почти в каждой сцене. В него входят, среди прочего:

- приоритет источников и правила канона;
- запрет превращать подготовку/candidate в сыгранный факт;
- управление Яром и формат повествования;
- характерные якоря Дафны, Лютобора и Рады;
- правила управления партией в бою;
- готовность заклинаний/экипировки и восстановление ресурсов;
- дорожные события;
- базовые принципы экономики Хейвенгарда.

Полные большие документы остаются в Google Drive. `source_registry` хранит их названия, Drive ID, роль и режим загрузки. Они загружаются **по необходимости**, а не целиком на каждом ходу. Например, полный экономический промт обязателен при закрытии месяца или глубоком экономическом аудите, а мастерская библия — только для релевантной подготовленной ветки.

`views/gm-context.md` автоматически строится из authoritative state + rule pack. `views/player-context.md` не содержит candidate-идей, скрытой подготовки или мастерских rule-pack инструкций.

## Знания и причинность

Поддерживаются:

- `canonical / candidate / disproven`;
- отдельные `beliefs` персонажей;
- `world_pressures`, двигающие мир независимо от игрока;
- активные/закрытые сюжетные линии;
- `commit_history`;
- защита от stale transaction;
- атомарность сложных изменений.

Ошибочный старый факт не должен молча исчезать: он переводится в `disproven`, а исправление хранится отдельно как `canonical`.

## Регрессионные сценарии и fixtures

Сценарные тесты **не запускаются от сегодняшнего живого state**.

Каждый устойчивый сценарий получает собственный замороженный baseline в `tests/fixtures/`. Благодаря этому кампания может уйти на месяцы или годы вперёд, а старый тест всегда начинается из одной и той же точки.

Первый такой сценарий:

- `tests/fixtures/road-bridge-baseline.json`
- `tests/test_road_return.py`

Он проверяет:

- завершение спасения у моста;
- одновременное изменение нескольких ресурсов;
- атомарный откат невалидной транзакции;
- Магическое восстановление Дафны после короткого отдыха;
- длительный отдых;
- невосстановление боеприпасов отдыхом;
- прибытие в Хейвенгард;
- население/продовольственный резерв;
- завершение дорожной линии;
- повторную загрузку state;
- построение GM/Player contexts;
- подключение постоянного rule pack;
- скрытие candidate-идей от player context.

Новый fixture-тест создаётся не после каждой сцены, а когда появляется **новый класс механики** или исправляется ошибка, которая не должна вернуться: закрытие месяца, таймеры проектов, сложный инвентарь, асимметричные знания, экономика, откат/снапшоты и т. п.

## Автоматические тесты

```bash
python tests/test_mvp.py
python tests/test_road_return.py
```

GitHub Actions запускает их автоматически при push/PR в `main`.

## Что пока остаётся следующими этапами

- полноценные игровые таймеры и календарь проектов;
- экономика как исполняемая подсистема, а не только набор правил;
- поселения и распределение рабочей силы;
- сложный количественный инвентарь;
- отношения как отдельная сущность;
- журнал транзакций отдельными неизменяемыми файлами;
- снапшоты и rollback;
- импорт/индексация старых летописей и промтов с автоматическим выделением постоянных правил.
